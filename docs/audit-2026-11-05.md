## Findings

### Medium

**FT1. Five external commands in request and probe paths have no deadline, in
a tree that bounds every other one.** *Medium, likely (the missing bound is
proven; the hang is a condition).*

- [processes.go:45-46](../internal/health/processes.go) — `exec.Command("supervisorctl", "-c", supervisorConf, "status")` and `CombinedOutput()`, no context.
- [cert.go:112](../internal/health/cert.go) — `exec.Command("postconf", "-h", "smtpd_tls_cert_file")`; since `2.16.1` this one is asked *again at each check* (the comment at :119-125 says so), not once at start.
- [sasl.go:298](../internal/app/sasl.go) (`saslpasswd2`) and [sasl.go:317](../internal/app/sasl.go) (`db_dump`) — in the path of every application create, save, password regeneration and delete.
- [cert.go:90](../internal/health/cert.go) (`postconf -x -h smtpd_banner`) is the same shape but runs once at start, where [retry.go:73](../internal/postfix/retry.go) also runs unbounded; neither is a leak.

The first two are called from the two busiest automatic paths the panel has:
`health.Liveness()` in the `/healthz` handler
([web.go:373-385](../internal/web/web.go)), which the image's `HEALTHCHECK
--interval=30s --timeout=5s` asks forever
([Dockerfile:199-200](../build/Dockerfile)), and `healthChecks()`
([handlers_status.go:647-668](../internal/web/handlers/handlers_status.go)),
which draws Health and its polled fragment
([health_body.html:15](../internal/web/view/templates/health_body.html)
carries `data-poll`; [panel.js:310-311](../internal/web/view/static/panel.js)
asks every 5 s while the operator is on the page, every 30 s while it is
idle).

Why it matters: a child that stops answering — supervisord wedged on a full
log filesystem is the realistic one — blocks its caller *for ever*. Docker
kills the probe's `curl` at 5 s, htmx gives the fragment up at 30 s
([panel.js:371](../internal/web/view/static/panel.js)), and the server's write
deadline ends the response at 60 s
([httpserver.go:148-157](../cmd/panel/httpserver.go)), but none of those ends
the handler's goroutine or reaps the child: `CombinedOutput` is still waiting.
With the Health page open on a desk that is one goroutine and one process
every 5 s, plus one every 30 s from the probe, against `pids_limit: 1024`
([docker-compose.yml:177](../deploy/docker-compose.yml)). At the ceiling
Postfix can no longer fork, so an unreadable Health page becomes a mail outage
— a long way from the symptom the operator first sees.

The tree's own convention is the opposite, which is what makes these five
stand out: `postqueue` gets 5 s
([queue.go:13,59](../internal/postfix/queue.go)), the notifier's `sendmail`
20 s ([mailer.go:18,105-114](../internal/notify/mailer.go)), and supervisord's
own XML-RPC 10 s over an `http.Client`
([rpc.go:74-79](../internal/supervisor/rpc.go)) — so `Reload` is bounded while
the `supervisorctl status` that reports it is not.

Fix: `exec.CommandContext` with a few seconds on all five, taking the request's
context where there is one (Health, the application forms) and
`context.Background()` with its own timeout where there is not (`/healthz`,
`postfixStarted`). A refused answer then grades the card `Unknown`, which
[handlers_status.go:649-656](../internal/web/handlers/handlers_status.go)
already renders.

**FT2. The compose file's build fallback has the deployment directory's parent
as its context — in the guide's own layout, the operator's home directory.**
*Medium, likely.*

[docker-compose.yml:30-34](../deploy/docker-compose.yml) is
`context: ${SELFPOST_SOURCE:-..}`, and the guide's step 1 puts the file in a
directory of its own — `mkdir -p selfpost/data selfpost/certs && cd selfpost`,
then `curl -O …/deploy/docker-compose.yml`
([guide.md:286-292](../docs/guide.md)) — so `..` is `/opt`, or the operator's
home. `SELFPOST_SOURCE` is the escape hatch and
[.env.example:14](../deploy/.env.example) carries it commented out.

[guide.md:370-378](../docs/guide.md) promises the fallback: "When the pinned
image is neither on the host nor on ghcr.io - or ghcr.io is out of reach -
`docker compose up` builds it from a clone of the repository instead of
failing", and the CHANGELOG for `2.16.5` records that Compose's build-on-missing
behaviour was measured. Both are right about Compose. What the measurement
covered is a clone: the guide's own sentence for this case is "The clone is the
parent of the compose file's directory **when the file is used from the clone's
`deploy/`**". In the layout step 1 creates, the parent is not a clone, so the
build first sends that whole tree to the Docker daemon as its context —
unbounded, and a home directory holds the operator's SSH keys and mail — and
then fails on `<parent>/build/Dockerfile: no such file or directory`. The
repository's [.dockerignore](../.dockerignore) does not apply: it is read from
the context root, which is not the repository. The result is slower, larger and
more confusing than the pull error it replaced, on the exact machine that has
just failed to reach ghcr.io.

Probe that settles it: on a host without the image, in a directory laid out as
step 1 says, with `SELFPOST_SOURCE` unset, `docker compose up -d` against a tag
ghcr.io does not have, and watch the "transferring context" line.

Fix, either of them one line: default the context to a path that cannot exist
by accident and fails at once naming itself (`${SELFPOST_SOURCE:-./source}`),
or move the `build:` block into a documented override file that the guide's
"build it from a clone" section tells the operator to add. Either way, one
sentence in § Fixed image tag about what happens when `SELFPOST_SOURCE` is not
set — the promise in that section is what an operator reads when the pull
fails.

### Low

**FT3. The reconcile sweep reads the log again for every row it closes.** *Low,
likely (arithmetic from the constants; not measured).*

[logtail.go:400](../internal/logtail/logtail.go) calls `resultInLog(path, row)`
for each row the sweep has just closed, and `resultInLog`
([:424-443](../internal/logtail/logtail.go)) asks `QueueLines` for the row's id
in `mail.log` **and** `mail.log.1`. `QueueLines` reads the last
`queueScanBytes` of each file — `4 << 20`
([:542](../internal/logtail/logtail.go), [:576-598](../internal/logtail/logtail.go))
— and substring-searches every line of it
([`mentionsQueueID`, :621-635](../internal/logtail/logtail.go)). So one closed
row costs up to 8 MiB of scanning, and the sweep closes every open row older
than the two-minute grace that Postfix no longer holds
([:390-404](../internal/logtail/logtail.go)).

That is exactly the shape of the outage the sweep exists for: a large deferred
backlog, the log rotated or lost while the panel was down. With the ~30k
messages [audit-2026-10-12](audit-2026-10-12.md) H3 measured, one sweep is up
to 240 GB of scanning, ahead of `countStuck` and the test-message close in the
same goroutine ([:327-331](../internal/logtail/logtail.go)), on a machine the
README sizes at 512 MB. The bytes come from the page cache after the first row,
so it is CPU rather than disk — minutes per sweep rather than hours — but it
repeats every five minutes for as long as the backlog lasts, and what it feeds
is a diagnostic counter (`reconcile_missed`).

Fix: collect the queue ids of the rows about to be closed and make one pass
over the two files per sweep, matching against that set — one 8 MiB read
instead of one per row. Or, above a threshold of closed rows, count the check
as a sample and say so in the log line.

**FT4. `architecture.md` says one live link per user and purpose; reset links
deliberately accumulate.** *Low, proven by reading.*

[architecture.md:1225-1227](architecture.md): "**`user_links`** — the one-time
links that confirm an address and reset a password (v13) … one live link per
user and purpose." The store does that for a confirmation link and, on purpose,
not for a reset one: [userlinks.go:30-46](../internal/store/userlinks.go)
deletes the user's previous link only when the new one is a `confirm` (the
doubled `purpose` condition — see **FT7**), for the reason in its comment:
"anyone who knows a username can ask for one, and a request of theirs must not
kill the link the user is about to open". With a 30-minute life, a 10-minute
spacing and five a day ([links.go:24-38](../internal/web/auth/links.go)), up to
three reset links are live at once.

Fix: one clause in architecture.md — "one live confirmation link per user;
reset links accumulate until taken or expired, bounded by the day's five and
their thirty minutes". The code is right; the as-built document should say what
it does.

**FT5. The Outbound log asks the store once per assigned domain, on a fragment
polled every five seconds.** *Low, proven by reading.*

[handlers_monitor.go:358-372](../internal/web/handlers/handlers_monitor.go)
loops over the assigned domains calling `ListApplicationsByDomain`, to build
the set of logins the `app` filter is checked against and the dropdown offers.
The log's fragment is one of the polled blocks
([panel.js:310-311](../internal/web/view/static/panel.js)), and every statement
waits its turn on the process's one database connection
([store.go:58-65](../internal/store/store.go)). And `ListApplicationsByDomain`
is not one statement: after draining the applications it asks once more per
application for its address rows
([applications.go:231,251-262](../internal/store/applications.go) — "Fill
address lists after the first query is drained (MaxOpenConns is 1)"). So a poll
costs one query per domain *plus one per application*, to draw a dropdown of
logins — on the connection the journal-milter's per-message rate-limit count
also queues on. The address lists are used by the message page's `sendsAs`, not
by this filter, and `ListApplicationLogins`
([applications.go:266](../internal/store/applications.go)) already returns
exactly what the filter needs and has no caller in the tree.

Fix: one query for the logins — `ListApplicationLogins` for the global role,
the same restricted to the assigned domain ids for everyone else.

*The same finding, with the per-application half of it and the unused store
method, is L2 of [code-review-2026-11-05.md](code-review-2026-11-05.md); the
two passes reached it independently and its reading is theirs.*

**FT6. `postqueueTimeout` is a constant, so the test of the size cap races it —
and lost on this machine.** *Low, proven (measured here).*

`go test ./internal/postfix` fails in `TestQueueIDsRefusesATruncatedListing`
([queue_test.go:51-63](../internal/postfix/queue_test.go)) with `QueueIDs on a
5 MiB listing = 0 ids, postqueue -p timed out after 5s; want the listing
refused for its size`, after 5.01 s. The test has to move 5 MiB out of a
re-exec'd test binary inside the product's own deadline
([queue.go:13](../internal/postfix/queue.go)), and unlike logtail's
`pollInterval`, `retentionInterval` and `queueScanBytes` — each a var "so tests
can shorten/shrink it" — `postqueueTimeout` cannot be moved. CI is green, so
today this is a slow-host artefact and tomorrow a flake on a loaded runner.

Two consequences are worth more than the test. One: in production the same
deadline covers the process start and the whole read, so on a busy host a
large-but-legitimate listing is reported as "timed out" rather than as "larger
than 4 MiB". Both mean "no information" to the sweep
([queue.go:104-119](../internal/postfix/queue.go)), so nothing is lost — but
the log line and the Health card say the wrong thing about a queue that is
merely big. Two: when the deadline fires after the cap was already reached, the
truncation the reader knew about is thrown away
([:66-68](../internal/postfix/queue.go)).

Fix: make `postqueueTimeout` a var, as logtail does, and shrink it in the test;
and in `listQueue` report the size cap when `out.truncated` is already true
even if the deadline fired too.

*The same failure appears in the machine results of
[code-review-2026-11-05.md](code-review-2026-11-05.md), diagnosed there as the
fake `postqueue` taking longer than the deadline to compose its listing, with
"the product path … not involved". The slowness is the test's; the deadline it
races is the product's own, and in production it also covers the process start
— which is what the two consequences above are about.*

### Nits

**FT7. `CreateUserLink`'s delete condition reads as a typo.**
[userlinks.go:43-44](../internal/store/userlinks.go): `WHERE (user_id = ? AND
purpose = ? AND purpose = ?) OR expires_at <= ?` with `(userID, purpose,
LinkConfirm)`. It is correct — the doubled column makes the first clause true
only when the link being created is a confirmation — but the reason sits in the
comment above, not at the line, and the next reader spends a minute deciding
whether it is a bug. Fix: an `if` in Go, or a condition that says what it means
once.

**FT8. A failed map rewrite after a delete puts the entry back under a new id.**
[lists.go:128-136](../internal/inbound/lists.go) re-adds the row it deleted
when `sync()` fails; `AddSpamListEntry` gives it a new id and a new "added"
stamp, so the page shows the same entry as another one and the operator's next
delete aims at an id that no longer exists. Fix: keep the row and report the
sync failure, as `Add` does in the other direction
([:100-108](../internal/inbound/lists.go)).

**FT9. The DNS checks do not take the request's context.**
[dnscheck.go:143,174,222,267](../internal/dnscheck/dnscheck.go) each build
`context.WithTimeout(context.Background(), c.timeout)`, so a client that
navigates away — or htmx at its 30 s — leaves the slowest page's lookups
running to their own end. It is bounded, and it fills the cache for whoever
asks next, which may well be the point; nothing in the file says so, and
[development.md](development.md) asks that a reliance of that kind be written
down where the code depends on it. Fix: a comment, or thread the request's
context and keep the cache write.

**FT10. Thirteen limiter sweepers run for the process's life with no stop.**
[auth.go:106-118](../internal/web/auth/auth.go) starts one goroutine and one
ticker per limiter ([ratelimit.go:46-56](../internal/web/auth/ratelimit.go));
they are the only goroutines in the tree with no context, and `Allow` sweeps on
its own, so nothing depends on them. Harmless in a supervised single-purpose
process — recorded here so the next reader does not hunt for the stop, and so a
future test that builds many modules does not quietly accumulate them.

## Confirmed as written (no action)

What a fresh read looked at hardest and found correct, so the next reader does
not redo it:

- **The store's concurrency and its migrations.** One connection for the whole
  process, WAL, `busy_timeout` and `_txlock=immediate`, so a writing
  transaction takes the lock at `BEGIN`
  ([store.go:33-77](../internal/store/store.go)); each migration re-reads
  `user_version` under that lock and skips one another process applied
  (:117-206); a 1.x file is refused by its `application_id` rather than
  half-migrated (:146-154). The database and its `-wal`/`-shm` are pinned
  `0600` because `/data` is world-traversable (:79-95).
- **The mail path's hot queries are indexed, and the plans are pinned by a
  test.** The per-message level-2 count goes by
  `idx_send_log_domain_id_created_at` / `idx_send_log_app_login_created_at`
  ([0008_tenant_boundary.sql:34](../internal/store/migrations/0008_tenant_boundary.sql),
  [0001_init.sql:141](../internal/store/migrations/0001_init.sql)), asserted
  with `EXPLAIN QUERY PLAN` in
  [queryplan_test.go:56-83](../internal/store/queryplan_test.go); the `unary +`
  in `appByLogin` that keeps the planner off the wrong index is cited
  ([stats.go:83-97](../internal/store/stats.go)). The two column-name
  interpolations in the tree are whitelist-gated
  ([deliverylog.go:15-38](../internal/store/deliverylog.go)).
- **A backup does not queue behind the panel.** The snapshot opens its own
  read-only connection for `VACUUM INTO`
  ([backup.go:494-526](../internal/backup/backup.go)), so the
  single-connection trade-off does not put the archive in the mail path's way;
  `mode=ro` makes a missing database fail instead of creating one, and the
  target path is generated, never user input.
- **Fail-open and fail-closed are where the documents say.** The chain is
  sender check `tempfail`, signer `tempfail`, journal `accept`
  ([postfix-config.sh:448-451](../build/postfix-config.sh);
  [architecture.md:403-412](architecture.md)), with bounded milter timeouts
  (:485-496). The level-2 limiter fails open on every error path and says so
  ([milter/ratelimit.go:20-30,37,61,78](../internal/milter/ratelimit.go)); a
  reservation is taken under the same lock as the count, so two sessions cannot
  spend one slot ([milter/inflight.go:47-68](../internal/milter/inflight.go)),
  and one never released expires (:8-23).
- **Authentication and its limiters.** Tokens are 256 random bits stored as
  SHA-256 ([token.go](../internal/web/auth/token.go),
  [session.go:42-63](../internal/web/auth/session.go)); a session that cannot
  be written is not handed out; two cookies of one name sign the request out
  ([auth/handlers.go:47-61](../internal/web/auth/handlers.go)); an unknown
  username costs a bcrypt comparison (:137-148,177-185); a right password
  refunds both buckets (:154-156); limiter keys are a /64 for IPv6 and a hash
  of the name, not the name
  ([limitkeys.go:27-63](../internal/web/auth/limitkeys.go)); the map is bounded
  and evicts blocked buckets only past a hard ceiling
  ([ratelimit.go:8-18,90-140](../internal/web/auth/ratelimit.go)).
- **The origin check.** `Sec-Fetch-Site` first, then `Origin`, then refusal;
  the opaque `null` origin and an unparseable one are refused; hosts are
  compared rather than whole origins because the panel speaks plain HTTP behind
  the proxy ([web/security.go:110-171](../internal/web/security.go)). It sits
  outside the auth middleware, so `/login` and `/setup/{token}` are covered
  (:54-59), and every `POST` in the route table is behind it
  ([web.go:213-336](../internal/web/web.go)).
- **RBAC is checked twice and answers 404.** The `/server/` subtree is wrapped
  at the router *and* each handler re-checks
  ([web.go:304-333](../internal/web/web.go),
  [handlers/authz.go:16-23](../internal/web/handlers/authz.go)); a delivery page
  compares the row's `domain_id` with the caller's reach and 404s rather than
  403s ([handlers_monitor.go:89-102](../internal/web/handlers/handlers_monitor.go));
  `ListDomainsForUser` honours `all_domains` in SQL, so *All* really includes a
  domain added later ([store/domains.go:87-94](../internal/store/domains.go));
  inbound reach is a separate grant
  ([auth/principal.go:54-80](../internal/web/auth/principal.go)).
- **SASL credentials cannot be lost half-way.** Copy, edit the copy, chmod,
  fsync the file, rename, fsync the directory, remove the copy on any failure
  ([app/sasl.go:69-146](../internal/app/sasl.go)); the password goes on stdin
  and `--` precedes the login (:158-198).
- **The secret file's cryptography.** scrypt at logN 15 (32 MiB) with a random
  salt, a random per-file nonce prefix, a counter nonce per 64 KiB chunk, and
  the header, counter and end-of-stream flag as additional data, so a chunk
  cannot be reordered, swapped between files or dropped
  ([secretfile.go:10-26,91-104,200-238,269-293](../internal/secretfile/secretfile.go)).
- **The version check leaks nothing and follows nothing.** Two anonymous GETs
  carrying no version, host name or cookie; bodies capped at 1 MiB; a `Link`
  header is followed only to the same registry, so a hostile answer cannot
  point the panel elsewhere
  ([update/update.go:6-11,192-256](../internal/update/update.go)).
- **The entrypoint's root phase.** `SELFPOST_HOSTNAME` is gated before anything
  else, because no fallback can be correct
  ([entrypoint.sh:10-53](../build/entrypoint.sh)); `/data`'s ownership and
  world-traversable mode are fixed once, as root, with the crash that taught it
  recorded (:55-77); the queue tree is handed to Postfix's users by name, twice,
  around `postfix check`, with `public/` and `maildrop/` kept in the setgid
  group (:224-270); `MILTER_WAIT_TIMEOUT` is validated before `expr` adds ten
  to it (:272-285).
- **The tailer's rotation handling.** It keeps reading the renamed inode for

  carries an inline `<script>`, an inline handler or a `style=` attribute — the

  no `unsafe-inline` and no `unsafe-eval`, with its fallback list cited

  conditional trigger ([panel.js:309-320](../internal/web/view/static/panel.js)).
- **CI publishes only what passed.** Actions pinned by digest, `permissions:

  staticcheck / test / govulncheck at every push and the e2e module compiled
  there ([test.yml](../.github/workflows/test.yml)); the release runs the e2e
  gate before it pushes, re-checks both binaries' version stamp immediately
  before the push, and runs govulncheck on the image's own binaries
  ([release.yml:93-135](../.github/workflows/release.yml)); the per-arch tag is
  re-pointed at the image rather than an index over it (:175-211); the GHCR
  cleanup builds its keep-list first and aborts before deleting anything

## Refactoring and optimisation

The owner's question of this pass: does the tree need refactoring, and where
does it need optimising? Short answer — **no refactoring; three optimisations,
all of them already findings above; one architectural decision with a trigger
to revisit.**

### Why no refactoring

- **The layering is real, not aspirational.**
  [architecture.md § Code layers](architecture.md) draws
  `cmd → web → services → store/adapters`, and the tree imports that way: 27
  packages, no cycles (the compiler forbids them), and the adapters are the
  only code that knows about Postfix, the milter protocol, DNS or the log file.
- **The seams the document names exist and are in use.** Thirteen narrow
  interfaces stand where an adapter meets a service —
  [app.SenderMaps](../internal/app/service.go),
  [domain.Applications](../internal/domain/service.go),
  [inbound.ListStore](../internal/inbound/lists.go) and `inbound.Maps`,
  [logtail.StatusStore](../internal/logtail/logtail.go) with `RefusalStore`,
  `SenderCheckStore` and `InboundStore`,
  [milter.Store](../internal/milter/milter.go) with `InboundStore` and
  `Refusals`, [notify.Store and notify.Sender](../internal/notify/notify.go) —
  and they are what the tests substitute. A tree that can be tested by
  replacing its adapters does not need reshaping in order to become testable.
- **Nothing is too big to hold.** The largest product file is 884 lines
  ([logtail.go](../internal/logtail/logtail.go)); fifteen of 142 exceed 500,
  and each of those is one subject — the send log's queries, the Health page's
  readings, the machine's `/proc` parsing. Splitting them by size alone would
  spread one argument over two files and separate the citation from the code it
  explains.
- **The duplication that exists is cheaper than its abstraction.** Seven
  handlers open with the same shape — parse a path id, look the object up,
  compare it with the caller's reach, render or 404 — and each then does
  something different. One generic version would be shorter and harder to
  audit, and the RBAC gate is exactly the line a reader must not have to infer.
  (An opinion, and the only recommendation in this file that is one.)
- **The expensive part of maintenance is already paid for:** the *why* of each
  block, with the version and the source it was read from
  ([development.md](development.md) § Code that relies on another component's
  behaviour). A refactor is what usually destroys that, and this tree has it in
  unusual quantity.
- **The tests are the reshape's real cost.** 188 test files and 35,208 test
  lines against 142 product files and 32,272 product lines — more test than
  product. Any restructuring carries them along or loses them.

### What is worth optimising, in order

1. **FT5 / their L2** — the polled Outbound log's one query per domain *and*
   one per application, every five seconds per open page, on the connection the
   mail path shares. One query; the store method that answers it already exists
   with no caller ([applications.go:266](../internal/store/applications.go)).
2. **Their L1** — one WAL commit per recipient inside the journal-milter's
   end-of-message callback, while Postfix waits in `cleanup`
   (`milter_content_timeout`, 30 s), and the inbound side batches the same shape
   on purpose ([inboundspam.go:107-140](../internal/store/inboundspam.go)).
   Measure it on the e2e stand before changing it, as that review says: if a
   thousand-recipient message costs seconds of commits, the batch is the fix.
3. **FT3** — the reconcile sweep's up-to-8 MiB re-read per closed row; one pass
   per sweep over the two files instead.
4. **FT1** is not an optimisation but it is the same work: putting a bound on
   what the panel waits for.

Everything else in this file is correctness, wording or hygiene, not speed.
Nothing found here suggests a hot path that is asymptotically wrong: the
per-message queries are indexed and their plans pinned
([queryplan_test.go:56-83](../internal/store/queryplan_test.go)), the log's
paged reads stop at their `LIMIT`, and the two bounded scans in the tree
(`TailLines`, `QueueLines`) read a budget rather than a file.

### The one structural decision with a revisit trigger

`db.SetMaxOpenConns(1)` ([store.go:58-65](../internal/store/store.go)). It is
deliberate, documented, and it removes a class of SQLite lock errors from a
process whose seven roles all write. Its price is that every reader queues
behind every other: the slowest page (the one that asks DNS, under a 60 s write
deadline), the retention sweep, and the journal-milter's per-message count are
one line.

The trigger to revisit is measurable rather than a matter of taste: when the
milter's per-message queries begin to *wait* — a level-2 count or an
`InsertQueued` approaching Postfix's milter timeouts (`milter_command_timeout`
15 s, `milter_content_timeout` 30 s,
[postfix-config.sh:485-496](../build/postfix-config.sh)). Past that the journal
fails open, so the message is neither journalled nor limited, and the sender
check and the signer tempfail, so mail is deferred. The cheap first step is not
a pool but a second, read-only connection for the panel's pages, leaving one
writer: WAL readers do not block it, and the write-first transaction discipline
([store.go:44-52](../internal/store/store.go)) is untouched. Do it *after*
items 1-3, which shorten the queue rather than widen the door.

### What this pass would decline to spend a week on

Splitting files for size; an ORM or a query builder, which would lose the
`EXPLAIN QUERY PLAN` pins; a front-end build step, which the CSP's absence of
`unsafe-inline`/`unsafe-eval` and the template guard tests depend on; a worker
pool or parallel milters, at the volumes [README](../README.md) sizes this
product for; and a Go rewrite of `build/postfix-config.sh` — it runs once at
start, it is where the Postfix citations live, and the e2e gates it.

**The test suite's cost** — the optimisation the other review measured — is
itemised in [code-review-2026-11-05.md](code-review-2026-11-05.md) § *The test
suite's cost, measured*; this pass's own timings, taken under load, agree
(`internal/web/auth` 254 s, `internal/web/handlers` 328 s, `internal/store`
175 s, `internal/web/view` 155 s). Its five recommendations are the right ones
in the right order — the bcrypt work factor as a variable first — and this file
has nothing to add to them.
